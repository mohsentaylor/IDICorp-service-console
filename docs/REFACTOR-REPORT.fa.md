# گزارش بازطراحی IDICorp Console — نسخه ۲٫۰٫۰

این سند توضیح می‌دهد که نسخهٔ قبلی (۱٫۱٫۰، مبتنی بر Vite) چه ایراداتی داشت،
برای هر ایراد چه راه‌حلی به کار رفت و چرا آن راه‌حل انتخاب شد.

---

## ۱. خلاصه

| موضوع | نسخهٔ قبلی (۱٫۱٫۰) | نسخهٔ جدید (۲٫۰٫۰) |
| --- | --- | --- |
| فریم‌ورک | React + Vite (SPA) | **Next.js 16** (App Router) |
| استایل | یک فایل CSS دستی حدود ۱۰۰۰ خطی | **Tailwind CSS v4** با توکن‌های طراحی |
| سرور | پوشهٔ `server/` با سه فایل و حدود ۳۰۰ خط کد دستی | پوشهٔ `server/` **حذف شد**. فقط یک `server.ts` کوچک برای WebSocket می‌ماند |
| ساختار | چند فایل بزرگ که منطق و ظاهر در آن‌ها قاطی بود | ساختار قراردادی Next.js و لایه‌بندی بر اساس SOLID |
| ساختار داده‌ها | پراکنده در چند فایل | همه در **یک فایل**: `src/types/index.ts` |
| تست | ۴۲ تست e2e با Playwright و ۱۵ تست integration | فقط **۶۴ تست unit** با Vitest، بدون مرورگر و سرور |
| مسیریابی | بدون URL (فقط state) | هر صفحه URL خودش را دارد: `/tasks`، `/calculator`، … |

## ۲. ایرادات نسخهٔ قبلی و راه‌حل‌ها

### ایراد ۱: سرور دستی در پوشهٔ `server/` کارهای خود فریم‌ورک را دوباره پیاده‌سازی می‌کرد

**مشکل:** فایل `server/index.mjs` با دست این کارها را انجام می‌داد: سرو کردن فایل‌های
استاتیک، تشخیص MIME، کش، جلوگیری از path traversal، هدرهای امنیتی، پراکسی HTTP و
پراکسی WebSocket. هر کدام از این‌ها جای خطای امنیتی و هزینهٔ نگهداری دارد.
علاوه بر این، همین منطق پراکسی یک بار دیگر در `vite.config.ts` برای حالت توسعه
تکرار شده بود. یعنی دو پیاده‌سازی از یک چیز وجود داشت که می‌توانستند از هم جدا شوند.

**راه‌حل:** پوشهٔ `server/` کامل حذف شد و هر مسئولیت به جای استانداردش در Next.js رفت:

| مسئولیت قبلی در `server/` | جای جدید |
| --- | --- |
| سرو فایل‌ها، کش، MIME، path traversal | خود Next.js |
| هدرهای امنیتی | `next.config.ts` → `headers()` |
| پراکسی `/api/*` | Route Handler: `src/app/api/[...path]/route.ts` |
| `/healthz` | `src/app/healthz/route.ts` |
| `/console/config` | حذف شد. Root Layout تنظیمات را مستقیم به کلاینت می‌دهد |
| خواندن و اعتبارسنجی env | `src/lib/config/settings.ts` |
| تبدیل احراز هویت echo | `src/lib/gateway/echoAuth.ts` (با تست unit) |

**چرا هنوز یک `server.ts` هست؟** دو محدودیت فنی واقعی این را لازم می‌کند:
1. Route Handlerهای Next.js نمی‌توانند اتصال WebSocket را upgrade کنند.
2. WebSocketِ echo در بک‌اند، هدر `Authorization: Bearer` را **در لحظهٔ handshake**
   می‌خواهد، و API استاندارد WebSocket در مرورگر اجازهٔ تنظیم هدر نمی‌دهد.

پس حتماً باید یک واسط سمت سرور وجود داشته باشد. `server.ts` همان الگوی رسمی
«Custom Server» در مستندات Next.js است. همهٔ درخواست‌های HTTP را به خود Next.js
می‌دهد و فقط دو مسیر `/ws/calculator` و `/ws/echo` را به بک‌اند وصل می‌کند.
این فایل حدود ۶۰ خط است و در پوشهٔ جدایی هم نیست.

### ایراد ۲: CSS دستی، بزرگ و با تعریف‌های تکراری

**مشکل:** فایل `style.css` حدود ۱۰۰۰ خط بود. چند کلاس دو بار تعریف شده بودند
(مثلاً `.muted`، `.fine` و `.badge` در انتهای فایل دوباره با رنگ دیگر بازنویسی شده
بودند). media queryها در چند جای فایل پخش بودند و حتی یک breakpoint (`760px`) دو بار
آمده بود. فهمیدن این‌که کدام قانون واقعاً اعمال می‌شود سخت بود.

**راه‌حل:** Tailwind CSS v4.
- رنگ‌ها و فونت فقط یک بار در `@theme` داخل `globals.css` تعریف شده‌اند
  (مثل `forest`، `ink`، `line`، `danger`).
- استایل هر جزء کنار خود همان جزء نوشته شده است. حالت موبایل و دسکتاپ با پیشوندهای
  `md:` و `xl:` در همان خط دیده می‌شود.
- استایل‌های مشترک (Button، Alert، Panel، Dialog) کامپوننت‌های قابل استفادهٔ مجدد
  شدند و دیگر کپی نمی‌شوند.
- استایل پایهٔ فرم‌ها و حلقهٔ focus برای دسترس‌پذیری با کیبورد در `@layer base` آمده است.

### ایراد ۳: کامپوننت‌های بزرگ با چند مسئولیت (نقض SRP)

**مشکل:** `Tasks.tsx` ۴۷۲ خط بود و این کارها را با هم انجام می‌داد: گرفتن داده،
debounce جست‌وجو، polling دوره‌ای، قفل mutation، دو دیالوگ و کل ظاهر صفحه.
`Calculator.tsx`، `Stream.tsx` و `Login.tsx` هم منطق شبکه و ظاهر را با هم داشتند.

**راه‌حل:** جدا کردن لایه‌ها بر اساس **Single Responsibility**:

```
features/tasks/TasksView.tsx       ← فقط ترکیب و نمایش
features/tasks/TaskItem.tsx        ← یک ردیف
features/tasks/TaskToolbar.tsx     ← جست‌وجو و فیلتر
features/tasks/TaskEditorDialog.tsx
features/tasks/DeleteTaskDialog.tsx
hooks/useTasks.ts                  ← state، polling، mutation
services/taskService.ts            ← فراخوانی API
lib/tasks/taskQuery.ts             ← منطق خالص (ساخت query، زمان انقضا)
```

همین الگو برای ماشین‌حساب (`useCalculator`)، echo (`useEcho`)، استریم
(`useStreamEcho`) و ورود (`useLogin`) هم اجرا شد.

### ایراد ۴: کامپوننت‌ها مستقیم با شبکه حرف می‌زدند (نقض DIP)

**مشکل:** آدرس‌هایی مثل `/api/tasks/${id}` و فراخوانی مستقیم `fetch` داخل JSX
نوشته شده بودند. تغییر API یعنی گشتن در همهٔ کامپوننت‌ها.

**راه‌حل:** لایهٔ `services/` (یعنی `authService`، `taskService` و `streamService`).
کامپوننت‌ها و hookها به متدهای معنادار وابسته‌اند (`taskService.update(...)`)
و از جزئیات HTTP خبر ندارند (**Dependency Inversion**). همهٔ درخواست‌ها هم از یک
نقطه یعنی `lib/api/httpClient.ts` می‌گذرند (timeout، لغو، پیام خطا، اعتبارسنجی پاسخ).

اصول دیگر SOLID هم رعایت شده‌اند:
- **Open/Closed:** کامپوننت `Button` با `variant` گسترش پیدا می‌کند، نه با تغییر
  کد داخلی‌اش. صفحه‌های جدید فقط یک خط به `lib/navigation/views.ts` اضافه می‌کنند.
- **Interface Segregation:** هر کامپوننت فقط propsی را می‌گیرد که لازم دارد
  (مثلاً `TaskItem` فقط `task`، `busy` و سه callback را می‌گیرد).

### ایراد ۵: ساختارهای داده پراکنده بودند

**مشکل:** نوع `Task` در `contracts.ts` بود و از `api.ts` دوباره export می‌شد. نوع
`Service` و `Channel` در `service.tsx`، کلاس `ApiError` در `api.ts`، و حالت‌های
اتصال فقط به شکل string خام در `useSocket.ts` وجود داشتند.

**راه‌حل:** فایل **`src/types/index.ts`** حالا تمام ساختارهای داده را در یک جا و
با توضیح دارد:
- DTOهای بک‌اند: `Task`، `TaskInput`، `TaskPatch`، `Captcha`، `LoginRequest`، `LoginResponse`
- پروتکل ماشین‌حساب: `CalculatorOperation`، `CalculatorRequest`، `CalculatorReply`
- state رابط کاربری: `SocketState` (به‌جای string آزاد)، `EchoEntry`، `StreamStatus`، `View`، `Session`
- پیکربندی: `ClientConfig`، `ServerSettings`، `SocketEndpoint`
- کلاس‌ها: `ApiError` و `InvalidResponseError`

### ایراد ۶: نبود URL برای صفحه‌ها

**مشکل:** صفحهٔ فعال فقط در `useState` نگه داشته می‌شد. دکمهٔ Back مرورگر کار نمی‌کرد،
نمی‌شد لینک یک ابزار را مستقیم باز کرد و همه چیز در یک کامپوننت `App` بود.

**راه‌حل:** مسیرهای App Router: `/login`، `/tasks`، `/calculator`، `/echo`، `/stream`.
- layout گروه `(workspace)` نقش **auth guard** را دارد: بدون session، کاربر به
  `/login?next=...` فرستاده می‌شود و بعد از ورود به همان صفحه برمی‌گردد.
- مقدار `next` فقط از بین مسیرهای شناخته‌شده پذیرفته می‌شود، تا کسی نتواند با یک
  لینک ساختگی کاربر را به سایت دیگری بفرستد (open redirect).

### ایراد ۷: پیکربندی با یک درخواست اضافه و یک قفل نسخهٔ شکننده

**مشکل:** کلاینت در شروع کار `/console/config` را می‌گرفت و اگر نسخهٔ سرور دقیقاً
برابر نسخهٔ build نبود (`service.release !== __APP_VERSION__`)، کل برنامه یک
صفحهٔ خطا نشان می‌داد.

**راه‌حل:** Root Layout که یک Server Component است تنظیمات را هنگام درخواست از env
می‌خواند و از طریق `ConfigProvider` به کلاینت می‌دهد. یعنی یک رفت‌وبرگشت شبکه کمتر،
و قفل نسخه‌ای هم وجود ندارد که بشکند.

### ایراد ۸: اجرا روی دستگاه دیگر در شبکهٔ محلی کار نمی‌کرد

**مشکل:** بک‌اند کوکی‌های `session` و `task_session` را احتمالاً با `Secure` می‌فرستد
(README قبلی هم می‌گفت روی LAN به HTTPS نیاز است). وقتی برنامه از گوشی یا کامپیوتر
دیگری با `http://192.168.x.x` باز شود، مرورگر کوکی Secure را دور می‌ریزد. نتیجه این
است که ورود موفق به نظر می‌رسد ولی همهٔ درخواست‌های بعدی `401` می‌گیرند.

**راه‌حل:** پراکسی در `lib/gateway/proxyHeaders.ts` کوکی‌ها را بازنویسی می‌کند:
- `Domain` حذف می‌شود و `Path=/` تنظیم می‌شود، تا کوکی به دامنهٔ خود کنسول بچسبد.
- فقط وقتی اتصال HTTPS یا localhost **نیست**، `Secure` حذف می‌شود و `SameSite=None`
  به `Lax` تبدیل می‌شود.

روی HTTPS هیچ ویژگی امنیتی کوکی کم نمی‌شود. این رفتار تست unit دارد، اما چون
اطلاعات ورود بک‌اند واقعی را نداشتم، با کوکی‌های واقعی آن تست زنده نشده است.

### ایراد ۹: اسکریپت‌ها و نسخهٔ Node

**مشکل:** `npm start` هر بار کل پروژه را از اول build می‌کرد. اسکریپت‌ها به
`node --env-file-if-exists` وابسته بودند که فقط در Node 22.12 به بالا وجود دارد.

**راه‌حل:** `build` و `start` از هم جدا شدند (روال استاندارد Next.js). فایل `.env`
با `@next/env` و به همان روش خود Next.js خوانده می‌شود. نسخهٔ لازم Node هم به
**20.9 به بالا** کاهش یافت (حداقل نسخهٔ Next.js 16). اجرای TypeScript سرور با `tsx`
انجام می‌شود که روی ویندوز، لینوکس و مک یکسان کار می‌کند.

### ایراد ۱۰: تست‌های سنگین و وابسته به محیط

**مشکل:** برای اجرای تست‌ها باید مرورگر Chromium نصب می‌شد (`npx playwright install`)
و چند سرور و backend آزمایشی بالا می‌آمدند. اجرای این تست‌ها کند و شکننده بود.

**راه‌حل (طبق درخواست، فقط unit):** Vitest با ۶۴ تست در ۱۰ فایل. همه زیر ۲ ثانیه
اجرا می‌شوند، بدون شبکه و بدون مرورگر واقعی:

| فایل تست | چه چیزی را پوشش می‌دهد |
| --- | --- |
| `contracts.test.ts` | اعتبارسنجی پاسخ‌های بک‌اند و توکن (از جمله header injection) |
| `echoAuth.test.ts` | رمزگذاری و رمزگشایی envelope احراز هویت echo و ورودی‌های مخرب |
| `settings.test.ts` | خواندن و رد کردن env نامعتبر |
| `proxyHeaders.test.ts` | بازنویسی کوکی، فیلتر هدرها، بررسی same-origin |
| `httpClient.test.ts` | نگاشت خطاها، 401 و انقضای session، لغو، خطای شبکه |
| `readUtf8Stream.test.ts` | UTF-8 چندبایتی شکسته بین chunkها، سقف ۱ مگابایت، لغو |
| `parseNumbers.test.ts` | قوانین ورودی ماشین‌حساب و تقسیم بر صفر |

## ۳. باگ‌هایی که هنگام بازطراحی پیدا و رفع شدند

این دو مورد در تست دستی کامل پیدا شدند و برای کسی که بعداً روی پروژه کار می‌کند مهم‌اند:

1. **پاسخ 401 در پراکسی به 502 تبدیل می‌شد.** وقتی بدنهٔ درخواست به شکل stream یا
   ArrayBuffer به `fetch` داخلی Node (undici) داده شود و بک‌اند `401` برگرداند،
   undici خطای «detached ArrayBuffer» می‌دهد. نتیجه این بود که «کپچای اشتباه» و
   «session منقضی شده» به شکل «سرویس در دسترس نیست» دیده می‌شدند. **راه‌حل:** بدنه
   به شکل `Blob` فرستاده می‌شود (این مورد جداگانه هم بازتولید و بررسی شد).
2. **focus دیالوگ.** `autoFocus` در React قبل از `showModal()` اجرا می‌شود و مرورگر
   focus را به اولین دکمه (✕) می‌برد. **راه‌حل:** کامپوننت مشترک `Dialog`، بعد از
   `showModal()` عنصری را focus می‌کند که با `data-autofocus` علامت خورده است.

## ۴. رفتارهایی که عمداً حفظ شدند

- توکن فقط در حافظه نگه داشته می‌شود (نه در localStorage). بنابراین بعد از reload
  باید دوباره وارد شد.
- کپچا از بک‌اند می‌آید و هیچ‌وقت در کلاینت پر یا محاسبه نمی‌شود.
- mutationها هیچ‌وقت خودکار تکرار نمی‌شوند. اگر نتیجه نامشخص باشد، به کاربر گفته
  می‌شود که ممکن است تغییر اعمال شده باشد.
- ماشین‌حساب: در هر لحظه فقط یک درخواست در جریان است، با مهلت ۱۰ ثانیه.
- echo: بعد از `ready`، هر پیامی محتوای کاربر حساب می‌شود، حتی JSONی که شبیه پیام
  کنترلی است.
- استریم: سقف ۱ مگابایت، مهلت ۳۰ ثانیه، و امکان لغو.
